SaudiEOU: Saudi Arabic End-of-Utterance Detection

From a SaudiBERT classifier to a privately deployed inference service: an Arabic web demo, tested API, Docker delivery, CloudWatch monitoring, and tracked model evaluation.

  • periodjan 2026 — present
  • rolesolo project
  • deploymentprivate AWS EC2

the problem

Has the speaker finished?

Reply too early and a voice agent can interrupt a speaker. Wait too long and the conversation becomes slow. SaudiEOU explores this problem by classifying Saudi Arabic text as COMPLETE or INCOMPLETE.

The project began with a hybrid dataset and SaudiBERT fine-tuning, followed by a LiveKit prototype for decisions on speech-to-text transcripts. I then built a separate serving application to make the classifier usable through an API and Arabic web interface.

architecture

From text to a served prediction

  1. Prepare data and fine-tune SaudiBERT

    Combined public Saudi-dialect text with 2,136 ALLaM-generated examples. Normalized text, generated incomplete samples, and balanced the training split. Compared SaudiBERT, MARBERTv2, and CAMeLBERT-DA before fine-tuning SaudiBERT for the binary classification task.

  2. Validate requests and run CPU inference

    FastAPI loads the Hugging Face classifier at startup. POST /predict requires an API key and accepts validated text up to 1,000 characters. It returns the predicted label and a model score. GET /health provides a service health check.

  3. Add an Arabic web demonstration

    A small HTML, CSS, and JavaScript interface calls the same inference path through /demo/predict, enabled by configuration. The web interface and API are packaged together in Docker and deployed on AWS EC2.

  4. Keep the deployment private

    The EC2 application is reached through an SSH tunnel, rather than a public HTTPS endpoint. The Hugging Face demo linked above is a separate model demonstration; it is not the private AWS deployment.

delivery & monitoring

Test, deploy, and observe

  1. Test the API and web interface

    Pytest checks cover valid and missing API keys, the homepage, demo predictions, and the disabled-demo configuration. Tests use a stub model to check application behavior without downloading model weights.

  2. Build versioned container images

    GitHub Actions runs tests and Docker builds. Successful main-branch pushes publish a container image tagged with the commit SHA, so a deployment can be tied to a specific source revision.

  3. Deploy through AWS Systems Manager

    A separately triggered workflow authenticates to AWS using OIDC and deploys through Systems Manager. A candidate container must pass health and prediction checks before promotion. The deployment script retains the previous container for rollback if the new release fails.

  4. Monitor inference requests

    Structured logs record prediction request paths, HTTP status codes, and latency in CloudWatch. A dashboard shows request activity, latency, and EC2 CPU utilization. An HTTP 5xx alarm connects to Amazon SNS email notifications; its notification path was tested manually.

internal evaluation

Evaluated the serving code on the existing test split and compared its predictions with a character-level TF-IDF + Logistic Regression baseline. MLflow records the comparison runs, parameters, metrics, artifacts, and model-selection decision.

SaudiBERT produced 109 INCOMPLETE-to-COMPLETE errors and 62 COMPLETE-to-INCOMPLETE errors, compared with 155 and 203 for the baseline. These are potential early or delayed response decisions inferred from text labels, not observed interruptions in live conversations.

The earlier 77.47% F1 figure refers to the COMPLETE class; macro F1 averages both classes. The comparison supported retaining the existing SaudiBERT deployment without retraining SaudiBERT or redeploying the service.

Evaluation scope: public and synthetic data were combined before splitting, and related truncated utterances may occur across splits. These scores are internal measurements, not independent estimates of production performance. External evaluation and manual review of the selected error sample remain unfinished.

deployment measurements

Measure latency and throughput

  1. Sequential requests

    A recorded EC2-local run completed 20 requests: 67.52 ms average latency, 68.50 ms P95, and 14.78 requests per second.

  2. Concurrent requests

    A recorded run completed 30 requests: 240.89 ms average latency, 287.17 ms P95, and 20.27 requests per second. Concurrency increased throughput while increasing response time per request.

These small runs used repeated input sent locally within EC2. They do not measure public internet latency, establish production capacity, or guarantee a service-level objective. The current monitoring alarm covers logged HTTP 5xx errors; complete instance downtime and model-quality drift require additional monitoring.
